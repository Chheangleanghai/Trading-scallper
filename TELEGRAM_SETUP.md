# Telegram and Vercel

1. Create a bot through Telegram's official BotFather; retain the token privately. Send your bot a message (or add it to the intended group with permission to post). Obtain the target chat ID from an authorized Bot API `getUpdates` response after sending a message. Do not use public third-party token-checking sites. No polling service is part of this project.
2. Generate a secret locally: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Use this generated value, not a sample. The handler requires at least 32 characters; use the 64-character generated hex string.
3. Import this project directory into Vercel. Set Node.js to 22.x. Use framework preset Other, no frontend build/output directory. For CLI deployment, run from this directory after signing in. Deployment has not been performed as part of this build.
4. Configure TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID, TRADINGVIEW_WEBHOOK_SECRET in Vercel environment variables for the desired environments. Redeploy after changing variables. `.env.example` contains names only. Vercel uses the package `engines` setting for Node22.
5. The endpoint is POST `/api/webhook`. For TradingView-compatible URL authentication, the rewrite maps POST `/api/webhook/SECRET` to `/api/webhook?secret=SECRET`. The handler requires the secret, application/json, and a valid payload. It uses constant-time comparison of SHA-256 hashes, not a request signature. TradingView is not expected to supply custom authorization headers or HMAC signatures.
6. Create the TradingView alert described in TRADINGVIEW_SETUP.md. Watch alert logs, Vercel responses and the phone notification. Use only non-sensitive test payloads; never paste secrets into issue reports, source control, screenshots or shared logs. URL secrets can appear in access logs—restrict log access and rotate exposed secrets.

The API returns 200 only after awaiting a successful Telegram JSON `ok:true`. It returns 400 for malformed signals, 401 for bad authentication, 405 for unsupported methods, 413 for application bodies >8 KiB, 415 for other content types, 503 for missing configuration and 502 for Telegram failure/timeout. Platform body limits may reject earlier. Unknown payload fields are ignored; core fields and any supplied recognized metadata must pass validation. Optional metadata includes executionModel, signalPrice, filledEntry (nullable), managedSl, targetSource, setupTimestamp, eventTimestamp, entryMode and status. Initial plan price ordering is validated independently of a tightened stop or slipped fill, which can legitimately cross earlier levels. Trade prices must be positive and strictly ordered by direction, scores within 0–100, timestamps positive safe-integer milliseconds through 2100. No freshness window is enforced: historical/manual test events are allowed. Authentication is essential.

The Telegram fetch timeout is 2.2 seconds; Vercel maximum duration is 10 seconds. TradingView's three-second request deadline includes overhead: cold starts or network delays can still cause lost/ambiguous delivery. A timeout can occur after Telegram accepted a message. There is no persistent storage, retry queue, durable deduplication, exactly-once guarantee or reliable replay prevention. Repeated requests intentionally send repeated messages. No in-memory dedupe claims are made. Responses do not expose tokens or upstream error bodies.

Messages escape all dynamic string markup, display actual signal prices and R ratios, and format the event timestamp in Asia/Phnom_Penh (UTC+7), falling back to plan time for older payloads. The plan timestamp is also shown in UTC. H1 context is frozen at plan confirmation. Signal price, planned entry and indicator/emulator filled entry are distinguished; initial SL and managed SL are separate. Notifications describe chart simulation, never a broker fill. V1 does not place trades.
